# 规则仓库整理：按「脚本 / 输入 / 输出」分层

## 结论

规则仓库原来的顶层叫 `ros/`，等于把"**谁消费**"当成了分类维度。结果源素材、生成脚本、手工清单、产物、
调度脚本全挤在一两层里：源素材以 URL 末段命名（`cncidr.txt`）看不出出处，加一个上游要改三四处，
而且服务器上还留着一份代码副本、与仓库双向回灌。

现在按"**处理**"来分：一条管线一个目录，固定 `sources.json` + `input/{upstream,manual}` + 处理脚本 + `output/`；
代码权威回到仓库，服务器只留数据。

## 问题

| 症状 | 具体表现 |
|---|---|
| 上游清单分散 | 一份在 `sources.json`，一份硬编码在 `gen_cn.py`，还有一份在 `fetch_bin.py` 的资产列表里 |
| 输入没有身份 | `src/` 下的文件名是 URL 最后一段，没有仓库、分支、commit、哈希，撞名就只能覆盖 |
| 输入输出同层 | 产物平铺在顶层，手工清单和生成脚本、调度脚本混在一个 `generator/` |
| 加减一个源要改多处 | 源清单 + 镜像白名单 + 日更脚本的拷贝清单 + 绝对路径，且横跨服务器与仓库两份代码 |

最后一个问题还带来一类隐性故障：服务器上那份代码是"真正在跑"的，仓库那份是留档，靠日更脚本按文件
列表回灌。**列表漏了哪个文件，仓库就悄悄落后于生产**——之前 `gen_cn.py` 就是这样漂移的。

## 改法

```text
README.md
scripts/
├── domain-rules/            域名 + CIDR 规则管线
│   ├── sources.json         ← 加减上游只改这里
│   ├── store.py             ← 取数 / 快照 / 记出处的唯一入口
│   ├── input/upstream/<owner>__<repo>/<path>   ← 原始快照 + _provenance.json
│   ├── input/manual/        ← 手工清单（网页可直接改）
│   └── output/              ← 产物
├── direct-ip/               直连 IPv4 管线（同结构）
├── _infra/                  mirror.py / publish.sh / 日更与快速通道入口
└── ros-side/                ROS 本地脚本留档（只存不跑）
```

几个关键取舍：

1. **上游引用写成 `owner/repo:path`**，分支从 `sources.json.upstreams` 取，完整 URL 由脚本拼。
   缓存路径直接就是 `<owner>__<repo>/<path>`，出处和文件一一对应，不需要额外对照表。
2. **每份快照配一个 `_provenance.json`**（url / 分支 / sha256 / 字节数 / 抓取时间），
   "这个文件哪来的、什么时候的"不用再翻日志。
3. **消费端只留档、不参与执行**：ROS 自带脚本能力，拉取和导入归它自己；Git 只负责产出可直接用的文件。
4. **服务器上跑仓库里的代码**：镜像服务加 `MIRROR_ROOT` / `MIRROR_REPOS` 两个环境变量后，
   systemd 直接执行仓库里的 `mirror.py`，`/srv` 只剩 Git 缓存与 HTTP 根。

## 手工改动的即时生效

原来手工清单改完只能等次日 06:00。现在补了一条按需通道（**不制定时、不做哈希**）：

```text
广州  /usr/local/bin/manual-refresh rules|direct-ip   # 只重生成手工部分，不拉上游
ROS   /system script run manual-refresh               # 拉取 + 导入 + 重载
```

ROS 侧那一步做两件事：地址表复用既有的六表同步；域名侧把 OxiDNS 的三份规则写进它的挂载目录，
再重启容器重载。**OxiDNS 的规则重载只有它内部的任务链能触发**（`rules_download` → `rules_reload`，
每天 07:00 由 cron 插件执行），没有对外的手动触发口，所以这里用整体重启容器来实现立即生效——
实测重启+恢复在 8 秒内，DNS 查询正常。

## 验证

- **产物逐行回归**：用新脚本重算，与线上在跑的产物逐行比对（忽略注释头），11 个文件全部一致；
- **单元测试**：直连 IP 管线 10 + 1 项全通过；
- **端到端演练**：手动跑日更入口，生成 → 发布 → 提交推送成功；直连管线单独跑一次也成功；
- **HTTP 一致性**：`/ros/` 下几个主要产物与仓库 `output/` 的 sha256 逐字节相同；
- **消费端**：ROS 上一次 `manual-refresh` 跑通，日志给出各文件字节数与解析结果，DNS 立即恢复。

## 回滚

1. 仓库：`git reset --hard <整理前的 commit>`；
2. 服务器：从备份目录取回 `/srv` 那份代码，systemd 指回它，`/usr/local/bin` 的四个入口软链指回旧路径；
3. ROS 与 OxiDNS 端**无需改动**——HTTP 路径与文件名这次完全没动。

## 可复用经验

1. **别用"谁消费"给仓库分层**。消费端会变、会加，用它命名顶层，等于把耦合写进目录名。
2. **输入要有出处**。文件名只是缓存键，不是身份；`_provenance.json` 这种并排的元数据文件，
   比事后 grep 日志便宜得多。
3. **"回灌列表"是隐形的技术债**。只要生产机上有一份"真正在跑"的代码，两份就迟早不一致；
   让它跑仓库里的代码，比维护一份同步清单可靠。
4. **加源的成本要压到一处**。判断标准很直白：新增一个上游，需要改几个文件？超过一个就该重构清单。
5. **没有手动触发口时，退而求其次要写清楚**。重启容器是个笨办法，但行为确定、可解释、可回滚，
   比猜一个未公开的接口稳。
