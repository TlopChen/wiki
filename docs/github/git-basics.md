```bash

git push                      # 推送到 GitHub
```

## 查看与回退

| 想做的事 | 命令 |
|---|---|
| 看改了什么（还没提交） | `git status --short`、`git diff` |
| 看最近几版 | `git log --oneline -10` |
| 看某一次提交动了哪些文件 | `git show --stat <commit>` |
| 丢掉某个文件尚未提交的改动 | `git restore <文件>` |
| 撤销最近一次提交，但改动留在工作区 | `git reset --soft HEAD~1` |
| 回滚一次**已经推送**的提交 | `git revert <commit>` |

两条原则：

1. **已经推送的提交不要改写历史。** `git reset --hard` 加 `--force` 推上去，会把别人的副本打断；要撤销就用 `git revert`，它生成一条反向提交，历史只增不改。
2. **提交前先 `git status`。** 确认没有把凭据、密钥、无关文件一起 `add` 进去。`git add .` 用得越多，这一步越不能省。

## 仓库怎么分层（2026-10-01 整理）

私有规则仓库踩过「按**谁消费**分层」的坑：顶层原来叫 `ros/`，把源素材、生成脚本、手工清单、产物全挤在一起——加一个上游要改好几处，上游文件名还是 URL 末段，看不出出处。

现在按**处理**分层，一条管线一个目录：

```text
scripts/
├── domain-rules/   域名 + CIDR 规则管线
├── direct-ip/      直连地址管线
├── _infra/         服务端分发与调度脚本
└── ros-side/       设备侧脚本留档（只存不跑）
```

每条管线固定 `README.md` + `sources.json` + 输入目录 + 输出目录，**人工维护的输入**和**程序生成的产物**分开放。约定：

- **加减上游只改 `sources.json`**，解析逻辑不写死来源；
- **输入要有出处**：每份上游快照旁边配一个元数据文件，记 url、分支、哈希、抓取时间，「这个文件哪来的」不用翻日志；
- **输出目录不手改**，由脚本重新生成、由发布脚本拷到服务目录；
- 判断标准很直白：**新增一个上游要改几个文件？超过一个，就该重构清单了。**

复盘见[《规则仓库整理：按「脚本 / 输入 / 输出」分层》](../blog/posts/git-repo-modularization.md)。

## 别在服务器上放第二份代码

同一类教训的另一半：以前生产机上放一份「真正在跑」的代码，仓库那份只是留档，靠日更脚本按文件清单往回灌——**清单漏一个文件，仓库就悄悄落后于生产**，而且没人会发现。

后来改成让服务器直接执行仓库里的脚本（符号链接 + systemd 指向仓库路径），生产机上只留数据（缓存与产物）。「两份代码」这件事从机制上消失，也就不再需要维护那份回灌清单。

> 经验：**「回灌清单」是隐形技术债**。只要生产机上有第二份代码，两份迟早不一致；让它跑仓库里的代码，比维护同步清单可靠。

## 踩坑记录

- `LF will be replaced by CRLF` 警告：Windows 与 Linux 的换行符差异，无害，可忽略；想彻底消掉，用 `.gitattributes` 固定 `text eol=lf`。
- 密码、API token、内网拓扑**绝不提交进公开仓库**。公开仓库全世界可见。
- 仓库命名避免和工具重名（比如拿 `git` 当仓库名，找起来容易混）。
- Windows 上克隆到 NTFS 后，如果目录属主变过，git 会报 `dubious ownership`——用 `git config --global --add safe.directory <路径>` 或改用属主正确的副本，别急着 `chown`/改 ACL。
